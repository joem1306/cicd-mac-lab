From a code change
to a canary release

A practical, beginner-friendly CI/CD lab. Build a tiny website, test it on GitHub, publish a Docker image, deploy it locally, route one simulated client to the new version, then promote or roll back.

Honest simulation: One out of three clients = 33% of these three simulated client endpoints, not 10% of real users. It demonstrates deterministic client routing. Real 10% request-weighted or user-sticky canaries require a traffic router or feature-flag service; see the optional extension.

Costs: Docker Desktop is free for qualifying personal use; GitHub Free and GitHub-hosted Actions have usage limits. This tiny public-repository exercise should fit within free allowances, but review your account's current billing/usage settings. No paid cloud hosting is needed.

Credentials: This lab has no application login. The sample admin / pass123! credentials are deliberately not used: publishing fixed credentials in a public repository would be unsafe. GitHub authentication uses your own account and GitHub's built-in workflow token.

1 Prepare your Mac

Unzip the kit, then open Terminal in the extracted cicd-mac-lab directory. You can type cd and drag the folder into Terminal to insert its path.

docker version
docker compose version
git --version
node --version

You need Docker Desktop running, Git, and Node.js 22+ for local testing. If Node.js is missing, install an official LTS release from nodejs.org. GitHub Actions runs Node.js itself, so local Node is only needed to run the tests on your Mac.

Apple M4 is ARM64. The workflow builds both linux/arm64 and linux/amd64 image variants, so Docker Desktop on your M4 can pull the ARM64 variant.

Docker Desktop engine is running and both Docker commands succeed.
I have the unzipped kit open in Terminal.

2 Start the original website (v1)

Run these commands from the kit root:

npm test
./scripts/lab.sh init
./scripts/lab.sh status

The init command builds a local Docker image and starts the five containers with Docker Compose.

Client 1 ↗

BLUE v1.0.0

Client 2 ↗

BLUE v1.0.0

Client 3 ↗

BLUE v1.0.0

Expected: all three browser URLs display the blue VERSION 1.0.0 site. If port 8081/8082/8083 is already occupied, stop the conflicting service or adjust the host ports in compose.yaml.

Look inside Docker Desktop → Containers: you'll see a Compose project with stable, canary, and client1–client3.

Concept: client1 is not a browser. It is an Nginx proxy listening on port 8081. Your browser sends requests to that proxy; the proxy forwards them to the stable application container over Docker's private network.

3 Prepare your personal GitHub repository

  1. Sign in at github.com/new.
  2. Create a public repository named cicd-mac-lab under your personal account. Public is simplest for the free exercise and public container-image pulls.
  3. Do not initialize it with a README, license, or .gitignore: the downloaded kit already contains files.
  4. Choose Create repository. Copy the HTTPS URL, for example https://github.com/YOUR_USERNAME/cicd-mac-lab.git.
  5. On GitHub, visit Settings → Actions → General. Ensure GitHub Actions is permitted. Under Workflow permissions, if available, choose Read and write permissions; the workflow also explicitly requests packages: write. Organization policies may override these settings.

In Terminal, from the kit root:

git init
git branch -M main
git add .
git commit -m "Initial blue website and CI/CD lab"
git remote add origin https://github.com/YOUR_USERNAME/cicd-mac-lab.git
git push -u origin main

Replace YOUR_USERNAME with your actual GitHub username. GitHub may ask you to authenticate using a browser or credential helper. Your GitHub account password is not accepted as an HTTPS Git password. The easiest option is GitHub CLI (gh auth login) or an installed Git credential manager; otherwise use a personal access token with suitable repository permissions. Never put tokens into code or the public repository.

Optional but educational: after your first successful workflow, configure Settings → Branches / Rulesets to require the test status check before merging pull requests. Ruleset availability and enforcement vary by repository type and GitHub plan.

The GitHub repository shows server.js, Dockerfile, compose.yaml, and .github/workflows/ci.yml.

4 Watch CI build and publish v1

Open your repository's Actions tab → Test, build and publish image → latest run.

There are two jobs: test executes the Node test suite on a GitHub-hosted Linux runner; publish waits for tests to pass, then Buildx builds the container image and pushes it to GitHub Container Registry (GHCR).

On your Mac, get the full 40-character commit SHA:

git rev-parse HEAD

The image is tagged as ghcr.io/YOUR_USERNAME/cicd-mac-lab:sha-FULL_SHA. This lab uses a commit-specific tag to make version selection easy. For stronger artifact immutability in real production, deploy by the image's SHA-256 digest.

Make the image public (important)

GHCR packages are often initially private, even when the GitHub repository is public. On GitHub, go to your profile → Packages → cicd-mac-lab → Package settings → Change visibility → Public. If the package is not visible yet, wait until the publish job finishes. Confirm the package is public before the next command.

Now deploy the image that GitHub built (not your local image):

./scripts/lab.sh deploy-stable YOUR_USERNAME cicd-mac-lab FULL_SHA
./scripts/lab.sh status

Replace both placeholders. This pulls the GHCR image, changes STABLE_IMAGE in your local .env, recreates the stable container, and reloads the three proxies. All three URLs should still show blue v1.

Checkpoint: You have now completed real CI (GitHub-hosted tests and build) and a manual CD deployment (your Mac pulling and running the published image). GitHub cannot directly reach Docker Desktop on your private laptop by default; the lab intentionally makes the local deploy command visible rather than pretending it is automatic.

5 Make a visible code change for v2

Open version.json in any text editor. Replace the entire file with:

{
  "version": "2.0.0",
  "headline": "Welcome to the GREEN release!",
  "message": "This is the new checkout experience. Canary is live!",
  "color": "#16a34a"
}

Save, then create a feature branch and push it:

git switch -c feature/green-release
npm test
git add version.json
git commit -m "Change website to green v2"
git push -u origin feature/green-release

On GitHub, click Compare & pull request, create a PR targeting main, and inspect the Actions run. A PR runs tests but does not publish an image. Merge the PR only after tests pass.

Back on your Mac:

git switch main
git pull --ff-only origin main
git rev-parse HEAD

Wait for the new main Actions run to finish successfully, then copy the new full SHA. The new published image is v2.

The PR tests passed.
The merged main workflow published the green v2 image.
Deliberate failure experiment: Before merging, try changing version to banana, then run npm test. The validation test fails. Restore 2.0.0 and re-run. This demonstrates why CI can block broken changes.

6 Deploy v2 to canary and expose one client

First pull the new GitHub-built image into the canary container:

./scripts/lab.sh deploy-canary YOUR_USERNAME cicd-mac-lab NEW_FULL_SHA
./scripts/lab.sh status

At this point all clients should still show blue v1: the canary container exists, but nobody is routed to it yet. This is an important distinction between deploying and releasing.

Now switch only client 1:

./scripts/lab.sh route-canary
./scripts/lab.sh status
Client 1 ↗

GREEN v2.0.0

Client 2 ↗

BLUE v1.0.0

Client 3 ↗

BLUE v1.0.0

Open the three URLs side by side. Refresh them. Look at routing/client1.conf: its proxy_pass now points to http://canary:3000, while clients 2 and 3 still point to http://stable:3000.

To manually smoke-test the versions:

curl -s http://localhost:8081/api/info
curl -s http://localhost:8082/api/info
curl -s http://localhost:8083/api/info

Observation exercise: leave the canary exposed for a few minutes, refresh it, and inspect logs:

docker compose logs --tail=30 canary
docker compose ps

This lab does not implement automated metrics or a three-hour promotion gate. Your manual checks are the release gate. The objective is to understand routing before adding automation.

Try reverting the canary exposure without changing any image:

./scripts/lab.sh route-stable

Client 1 should return to blue. Then use ./scripts/lab.sh route-canary to restore the canary for the next step.

7 Promote v2 to all three clients

When you've verified client 1 is healthy, run:

./scripts/lab.sh promote
./scripts/lab.sh status

The script saves the previous stable image in .previous-stable-image, changes the stable service to the v2 image, and points client 1 back to stable. Now all three URLs should show GREEN v2.0.0.

Client 1

GREEN v2

Client 2

GREEN v2

Client 3

GREEN v2

What changed? We did not rebuild the image. We promoted the already-tested canary image to stable and changed the proxy routing. That's the difference between creating an artifact and deploying it.

8 Practice rollback

Pretend users report a problem with v2. Restore the saved previous stable image:

./scripts/lab.sh rollback
./scripts/lab.sh status

All three clients should show BLUE v1.0.0 again. The v2 canary container may still exist, but the proxies now route to the restored stable service.

To stop the lab:

./scripts/lab.sh stop
Rollback scope: This restores the previous application image and routes, not database state. This demo has no database. In real systems, database migrations and external side effects require separate rollback strategies.

Optional next lab: real 10% of traffic

Replace the three static client proxies with a traffic router that supports weighted backends (for example Traefik with weighted services, or a suitably configured Nginx upstream). Send 1,000 requests and count how many reach v2. Then add Prometheus metrics, a threshold, and an automatic promotion/rollback controller. That is a separate, more advanced lab; this kit intentionally teaches one-client canary routing first.

Optional next lab: fully automatic local deployment

Install a self-hosted GitHub Actions runner on your Mac, or run a local agent that polls your image registry. Such a runner could execute the deployment script after CI passes. It is more powerful but carries security risks, especially with public repositories and untrusted pull requests. Do not expose your Mac's Docker socket to untrusted CI jobs.

Troubleshooting

GitHub Actions publish fails: permission denied

Check the workflow has packages: write and repository Actions permissions permit publishing. Check the Actions job logs. GHCR package linkage/ownership permissions can also affect writes.

docker pull says denied or unauthorized

Confirm the Actions publish job succeeded, you used the exact full SHA from the main commit, and the GHCR package was changed to public. The image name must be lowercase; the script lowercases owner and repo.

One of the browser URLs returns 502

Run docker compose ps, then docker compose logs stable canary client1. Check whether the backend app started and whether you changed a proxy config. Try ./scripts/lab.sh route-stable.

All clients show the same version after canary routing

Check that CANARY_IMAGE and STABLE_IMAGE differ in .env. Confirm you used the new SHA for the canary. Refresh the browser or use the no-cache /api/info endpoint.

Git push asks for a password

GitHub no longer accepts the account password for Git-over-HTTPS authentication. Use GitHub CLI and gh auth login, a credential helper, or a properly scoped personal access token.

Mac ARM architecture mismatch

Wait for the multi-platform publish job to finish. The workflow publishes both ARM64 and AMD64 variants; inspect the image manifest if necessary. Local docker build on your M4 normally produces an ARM64 image.

Reset the whole local lab

./scripts/lab.sh stop
rm -f .env .previous-stable-image
git restore routing/
./scripts/lab.sh init

Note: git restore routing/ discards your local proxy-routing edits. The kit doesn't delete your GitHub repository or published packages.
